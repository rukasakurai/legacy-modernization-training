# GitHub Copilot Spaces Q&A

## TL;DR
- **Spaces**: プロジェクト固有のドキュメント・コンテキストをLLMに提供する仕組み（レポジトリスコープ）
- **Custom Instructions**: 開発者個人のコーディングスタイル・優先事項を指定（ユーザースコープ）
- **優先順位**: System > Custom Instructions (スタイル) > Space 検索ドキュメント
- **ベストプラクティス**: Spaceは小規模かつ焦点を絞り、Markdownを優先、重複を避ける

## Q&A

### Q1: Copilot Spaces vs Custom Instructions vs カスタムVS Code拡張 / MCPサーバーの違いは？

**比較軸**:
- **意図**: Spaces = プロジェクト共有知識、Custom Instructions = 個人スタイル、拡張/MCP = 専用ツール統合
- **スコープ**: Spaces = リポジトリレベル、Custom Instructions = ユーザー全体、拡張/MCP = ワークスペース/グローバル
- **所有権**: Spaces = チーム共有（リポジトリ）、Custom Instructions = 個人、拡張/MCP = 開発チーム
- **複雑性**: Spaces = 低（ドキュメント配置のみ）、Custom Instructions = 最低、拡張/MCP = 高（コード開発必要）

**使い分けのヒント**:
- チーム全体でドメイン知識やアーキテクチャを共有 → **Spaces**
- 個人のコーディング規約・命名規則を統一 → **Custom Instructions**
- 外部APIやデータベースへの動的アクセスが必要 → **拡張/MCP**

### Q2: Office（Excel / PowerPoint / Word）ファイルを参照できる？

**技術的には可能だが推奨されない**:
- Spaceに配置すれば読み込み対象となるが、バイナリ形式は解析効率が低い
- トークン消費が大きく、関連性の判定も困難

**推奨アプローチ**:
- 重要な情報をMarkdownまたはプレーンテキストに変換して配置
- 表やデータは CSV や Markdown table として抽出
- 大規模なOfficeドキュメントは要約版を別途作成
- バイナリファイルはサイズとトークン効率の観点から避ける

### Q3: Spaceのコンテンツは実際にどう送信される？スコープを小さく保つ理由は？

**検索ベースの取得**:
- Space内の全ドキュメントが常に送信されるわけではない
- ユーザーの質問やコンテキストに基づき、関連性の高い部分のみをLLMに送信
- トークン予算は限られており、無関係なドキュメントは除外される

**小規模Spaceが重要な理由**:
- 関連性の高い情報が確実に取得される（ノイズ削減）
- トークン効率が向上し、より多くのコンテキストを活用可能
- 検索精度が上がり、必要な情報へのアクセスが高速化
- サイズが大きいとトークン制限に達し、重要な情報が切り捨てられる可能性

### Q4: 複数のガイダンス（Spaces、Custom Instructions）が重複した場合の優先順位は？

**優先順位（高→低）**:
1. **システムプロンプト**: GitHub Copilot の基本動作定義（最優先）
2. **Custom Instructions**: 個人のスタイル設定（コーディング規約、言語選好など）
3. **Space検索ドキュメント**: プロジェクト固有の技術ガイドライン

**運用指針**:
- 技術的な正規ガイドライン（アーキテクチャ、API仕様、コーディング標準）は **Space** に配置
- Custom Instructions は軽量に保ち、個人の命名規則や形式的な好みに限定
- 重複や矛盾を避けるため、Space と Custom Instructions の役割を明確に分離

## ベストプラクティス

- **焦点を絞る**: Spaceは特定ドメイン・プロジェクトに限定し、1つのテーマごとに1つの権威あるSpaceを作成
- **厳選されたコンテンツ**: 必要最小限の高品質ドキュメントのみを含める
- **Markdownを優先**: バイナリやOfficeファイルは避け、プレーンテキスト/Markdownに変換
- **サマリーファイル**: 大規模ドキュメントには `README.md` や要約ページを追加し、全体像を提供
- **定期的な整理**: 古いドキュメントや無関係な情報を削除し、常に最新状態を保つ
- **重複を回避**: Custom Instructionsとの役割分担を明確化し、同じ内容を両方に記載しない
- **ドメインごとに1つ**: 同じトピックに対して複数のSpaceを作成せず、集約する
- **アクセシビリティ**: チームメンバーが理解しやすい構造と命名規則を採用
